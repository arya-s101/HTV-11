# Change PRD v4 — Sound, fresh questions, no timers, skip, rich character profile, multiplayer

> Applies on top of `PRD.md` and `PRD-changes-v3.md`. Where documents conflict, **the newest wins** (v4 > v3 > PRD.md). Everything not mentioned here stays as specified.

## Summary of changes

1. **Sound on by default**, effects clearly louder than background music.
2. **Fresh questions every game** using the Gemini API, safely (facts and answers stay reviewed; Gemini varies the story and wording).
3. **No timers anywhere**, and a **Skip** button on every question.
4. **Rich character profile**: career, interests, needs, culture-related preferences and more, used to tailor the game — only from what the player explicitly states.
5. **Multiplayer**: Firebase anonymous auth + room codes.

**Suggested build order** (cheapest and safest first): 3 → 1 → 2 → 4 → 5. Multiplayer is the largest and riskiest change; build it behind a feature flag so single-player stays demo-ready at all times.

## Change 1 — Sound effects on by default

### Requirements
- Sound effects exist already for correct / wrong (verify; add any missing): **correct, wrong, skip, round start, reveal, stat card appear (soft), report card fanfare, button tap (subtle), player joined (multiplayer)**.
- **On by default.** Browsers block audio until a user gesture, so unlock the audio context on the first tap (the character creator's first interaction or the Start button). Never try to autoplay before that.
- **Mix:** two channels, `music` and `sfx`.
  - Default `music` volume ~0.25, `sfx` ~0.8.
  - **Duck** music to ~40% of its level while any effect plays, restoring over ~300ms.
  - Effects must always be clearly audible over music at default settings.
- Settings: master mute, music volume, effects volume. Persist in `localStorage` (wrapped in try/catch).
- Sound never carries meaning alone: correct/wrong is also shown visually (existing rule).

### Supersedes
- `PRD.md` §5.10: "muted by default" → **on by default**.

### Acceptance criteria
- [ ] First tap unlocks audio; no console autoplay errors.
- [ ] Every listed event plays its effect.
- [ ] At default volumes, effects are clearly louder than music; music ducks during effects.
- [ ] Mute and both sliders work and persist across reloads.

## Change 2 — Fresh questions each game (Gemini)

### Problem
Questions repeat across games because the pool is small and fixed.

### Principle
**Gemini varies the scenario; reviewed content decides the facts and the answer.** This keeps the existing rules: LLMs never create costs, figures, legal content, or the correct answer (`PRD.md` §7).

### What Gemini generates
- The **scenario framing** of a question: who, where, what's happening, written for the player's character and profile (Change 4). E.g. the same "get repairs requested in writing" lesson framed as a broken heater in January, a leaking tap, or a dead fridge.
- **Listing text** for Spot the Fake and Pick Your Place, built around features **chosen by code** (e.g. code decides "price 40% under benchmark", "asks for deposit before viewing", "utilities: unknown"); Gemini writes prose that expresses those features.
- Host one-liners and reactions (flavour only).

### What Gemini never generates
- **Numbers.** Gemini output uses placeholders (`{rent}`, `{benchmark}`, `{fare}`, `{hours}`); code fills them from `Field`s. **Any digit in Gemini output = reject.**
- **Answer options and the correct answer.** These come from reviewed per-ContentItem pools (`correct` variants and `distractors`), sampled and shuffled by code.
- Legal or tenancy claims, sources, stats, or anything shown in a stat card.

### Data shape

```ts
type QuestionTemplate = {
  id: string;
  content_id: string;                 // ContentItem it teaches (sourced)
  round: string;                      // "spot_the_fake" | "pick_your_place" | ...
  scenario_brief: string;             // instruction for Gemini: what situation to write, what it must include
  required_features?: string[];       // code-chosen features Gemini must express (listing rounds)
  correct_variants: string[];         // reviewed, ≥2
  distractors: string[];              // reviewed, ≥4; each verified wrong
  fallback_scenarios: string[];       // reviewed, ≥3, used when Gemini is unavailable
};
```

Gemini returns:

```json
{ "scenario": "string with {placeholders} only, no digits", "host_line": "string" }
```

### Validation (all in code, before display)
1. Valid JSON matching the schema.
2. No digits; only known placeholders.
3. Length limits (scenario ≤ 3 lines × 15 words on screen, per the game-show text rules; longer goes to "Why?" only if reviewed — so in practice, reject if too long).
4. Listing rounds: each `required_feature` is expressed (keyword/phrase check per feature, defined in the template).
5. Blocklist: legal terms that would imply a legal claim (e.g. "illegal", "law says", "you have the right") → reject. Profanity → reject.
6. On any failure: retry once, then use a `fallback_scenario`. The player never waits on or sees a failure.

### Variety without repetition
- Each game samples templates, correct variants and distractors with a fresh seed; answer order is shuffled.
- Keep the last ~3 games' template IDs in `localStorage`; prefer unseen templates.
- Pre-generate in the background during character creation (batch request, one call per round), so questions are ready when play starts.

### Where calls happen
- Gemini is called only via the server-side proxy (Firebase Cloud Function, see Change 5). The key is never in the client.
- Proxy limits: per-session and per-room request caps, timeout ~6s, low temperature for listing rounds.
- **Base game must remain fully playable with zero Gemini calls** (fallbacks). Live generation is on by default when reachable.
- **Demo preset uses fallbacks only**, for a reproducible demo.

### Supersedes
- v3 Change 1: "Base makes zero LLM/API calls" → **Base may call Gemini for scenario variety but must work with zero calls.**

### Acceptance criteria
- [ ] Two consecutive games show different scenarios and different option sets/orders for the same round.
- [ ] Unit tests: outputs containing digits, unknown placeholders, missing required features, legal-claim terms or bad JSON are rejected and fall back.
- [ ] With the API blocked, a full Base game plays with fallbacks and no visible errors.
- [ ] Correct answers always come from `correct_variants`; no test can produce a Gemini-written option.
- [ ] Questions are ready before round 1 starts (no loading spinner mid-round on a normal connection).

## Change 3 — No timers; Skip on every question

### Requirements
- **Remove all question and round timers** (including Spot the Fake). Remove timer UI, state and tests.
- Every question screen has a visible **Skip** button (also keyboard shortcut, e.g. `S`).
- Skipping:
  - Briefly shows the correct answer in one line, then continues (tap to continue immediately).
  - Scores zero points; counts as "skipped" on the report card (separate from wrong).
  - Earns no receipt (e.g. skipping Move-In Day means no photos receipt — the later consequence still applies, which is the lesson).
  - Still shows the stat card (which itself is skippable).
- Unlimited skips. The old limited "skip" lifeline is removed; other lifelines stay.

### Supersedes
- `PRD.md` §5.3 "within a time limit"; §5.10 "Timers on rounds…" and the skip lifeline; v3 Change 2 "keep the Spot the Fake timer".

### Acceptance criteria
- [ ] No timer appears anywhere; no timer code remains.
- [ ] Skip works on every question, by button and shortcut; can't double-fire.
- [ ] Report card shows correct / wrong / skipped counts separately.

## Change 4 — Rich character profile and tailoring

### Goal
The player can tell the game as much about who they are as they want, and the game feels written for them. **All fields optional.** The Base game must still start fast.

### Two paths
- **Quick start** (default): name, sprite, age, career — then play. Randomize button stays.
- **Tell us more** (expandable): the full profile below. Can also be edited between rounds/stages.

### Profile fields

| Group | Fields | How the game uses it |
|---|---|---|
| Basics | Display name, age, pronouns | Host addresses the player correctly; age sets starting life stage |
| Look | Sprite layers, including clothing/accessory options reflecting different cultures (reviewed, respectful, original art) | Cosmetic only |
| Work / study | Career or field, workplace/campus area (pick from a list of Toronto areas), schedule (9–5, shifts, remote, hybrid) | Commute destination and trip count; scenario framing (e.g. night-shift worker and late-night transit) |
| Money | Income band (player picks, or "use a typical figure for my career") | Feeds calc as `player_input` or `illustrative` (see rules) |
| Household | Living alone / roommates / partner / kids; pets | Offer sizes, roommate scenarios, pet-related questions |
| Needs | Accessibility needs (e.g. step-free access, elevator), parking, quiet, in-unit laundry | Offer features and questions |
| Wants nearby | Free choice from a list plus free text: e.g. a specific grocery, place of worship, community centre, park, gym, nightlife, cultural community | Scenario flavour and offer descriptions ("10 minutes from the {wanted place}") |
| Interests | Hobbies (cooking, music, gaming, sports, art…) | Scenario flavour (a musician worrying about noise rules; a cook checking the kitchen) |
| Background | Newcomer to Canada / international student / grew up in Toronto / moved from elsewhere in Canada; languages spoken | Newcomer-relevant questions (no Canadian credit history, references); host flavour |
| Experience | First time renting? Rented before? | Starting difficulty suggestion |

### Tailoring rules (important)
- **Tailor only from what the player explicitly states as a preference or need. Never infer preferences from identity.** If a player says they want to be near a particular grocery or place of worship, use that. Never assume a player of a given culture, religion, language or background wants a particular neighbourhood, food, community or anything else.
- Identity fields never change prices, offers, landlord behaviour, difficulty, scam frequency or score. (Extends the existing appearance-is-cosmetic rule to every identity field.)
- Fields that genuinely change the renting situation (household size, pets, accessibility needs, newcomer status, income, workplace, schedule) may change offers and questions, but every such question uses reviewed, sourced content.
- Income: player-entered values get a new `Field` status **`player_input`**; "typical for my career" uses a sourced figure (e.g. Statistics Canada) or is labelled `illustrative`. Rent burden labels say which.
- Discrimination in housing is real. An **optional Extended event** may show a landlord asking something they shouldn't, using **only** sourced general information (e.g. Ontario Human Rights Commission), labelled not legal advice — and triggered randomly, never by the player's identity fields.
- Free-text fields: length-limited, profanity-filtered, shown only to the player (never in multiplayer, never in shared report cards).

### Privacy
- The profile is stored **on the device only** (`localStorage`, try/catch), with a "Clear my profile" button.
- Only fields the player has filled are used, and only these are ever sent to Gemini: career/field, schedule, household type, pets, needs, interests, "wants nearby" items, newcomer/first-time-renter flags. **Never sent:** name, pronouns, languages, background beyond the newcomer flag, free-text identity details.
- A one-line notice in the profile screen says what's used for personalization and that it stays on the device except for anonymous scenario requests.
- Nothing from the profile is written to Firebase except the multiplayer display name and sprite (Change 5).

### Acceptance criteria
- [ ] Quick start reaches round 1 in ≤4 taps after the title screen.
- [ ] All profile fields optional; the game works with every field empty.
- [ ] Test: changing any identity field (culture-related look, languages, background, pronouns) with the same seed produces identical prices, offers, landlord configs, scam counts and scoring.
- [ ] Stated "wants nearby" and interests visibly appear in scenarios.
- [ ] Gemini request payloads contain only the allowed fields (test on the proxy request).
- [ ] "Clear my profile" removes all stored profile data.

## Change 5 — Multiplayer (Firebase anonymous auth + room codes)

### Format
Party mode, game-show style: everyone plays the **same questions at the same time** on their own device; a live scoreboard between questions; the host controls pacing. Works with 2–8 players.

### Flow
1. **Host** taps "Multiplayer → Create room". Anonymous sign-in; a room is created with a **6-character code** (no ambiguous characters: no 0/O, 1/I/L).
2. **Players** tap "Join", enter the code and a display name, pick a sprite (Quick start only).
3. **Lobby** shows joined players with their sprites. Host chooses mode (Base / Extended), difficulty, and starts.
4. **Questions:** the host's client requests the round's questions once (Gemini via proxy, or fallbacks) and writes them to the room so everyone sees identical questions and option order.
5. **Answering:** each player answers or skips (no timers). Host sees who has answered and taps **Reveal** when ready (auto-reveal when everyone has answered).
6. **Reveal:** correct answer, each player's result, points, then the stat card, then a scoreboard.
7. **End:** shared scoreboard + each player's own report card on their device + "Play again" (same room) or "Leave".

### Multiplayer-specific rules
- **No personal profile data in multiplayer.** Only display name + sprite are synced. Questions use generic (non-personalized) scenarios so every player sees the same thing.
- Negotiation (LLM landlord) is **single-player only** for now.
- Host leaves → host role passes to the longest-connected player. Player disconnects → can rejoin with the same code on the same device (anonymous UID persists).
- Rooms expire after 2 hours of inactivity or when everyone leaves.
- Display names: ≤16 chars, profanity-filtered, unique within the room (append a number if taken).
- Max 8 players per room; joining a full or started room shows a clear message (late joiners can spectate if time allows; otherwise "game in progress").

### Firebase setup
- **Auth:** Anonymous sign-in only.
- **Firestore** (suggested structure):

```
rooms/{code}
  hostUid, status ("lobby" | "playing" | "reveal" | "finished"),
  mode, difficulty, seed, currentQuestionIndex, createdAt, lastActivityAt
rooms/{code}/players/{uid}
  displayName, sprite, score, joinedAt, connected
rooms/{code}/questions/{index}
  round, scenario, options[], (no answer key until reveal)
rooms/{code}/answerKeys/{index}
  correctIndex                     // readable by players only after reveal
rooms/{code}/answers/{index}_{uid}
  choice | "skip", answeredAt
```

- **Security rules** (must-haves):
  - Only signed-in users; only room members read room data.
  - Only the host writes room status, questions, answer keys and `currentQuestionIndex`.
  - A player writes only their own player doc and their own answer, **once per question**, only while status is `playing`.
  - Players can read `answerKeys/{index}` only when `currentQuestionIndex > index` or status is `reveal` for that index.
  - Scores: computed and written by a Cloud Function on reveal (or by the host client for the hackathon build, noted as a known limitation).
- **Cloud Functions:** the Gemini proxy (holds the key, rate-limits per room and per UID), room-code generation with collision check, score calculation on reveal, scheduled cleanup of expired rooms.
- **Presence:** update `connected`/`lastActivityAt` on a heartbeat (or Realtime Database presence if preferred).
- Firebase config in env variables; no service keys in the client bundle.

### Acceptance criteria
- [ ] Two browsers (one incognito) can create and join a room by code and play a full Base game together.
- [ ] Both clients always show the same question, option order and stat card.
- [ ] A player can't see the correct answer before reveal (verify with Firestore rules tests / emulator).
- [ ] A player can't answer twice, answer for someone else, or change room state (rules tests).
- [ ] Host leaving transfers host; a disconnected player can rejoin.
- [ ] No profile fields besides display name and sprite appear in Firestore.
- [ ] Single-player works with multiplayer disabled by feature flag, and with Firebase unreachable.
